# Let There Be Flight (LTBF)

Cyberpunk 2077 mod: flight for all vehicles. RED4ext C++ plugin + redscript + TweakXL tweaks + ArchiveXL archive + FMOD audio banks. Everything ships under `red4ext/plugins/let_there_be_flight/` (scripts, tweaks, archive, inputs are all loaded from the plugin folder, not r6/archive dirs).

Goal: the city should be flyable as it looks. That covers removing hidden colliders (collision with nothing visible) that make flying round the city harder, and adding collision where the game draws something solid but gives it none (`tools/world/proxy_colliders.py`). To see what the planner treats as solid along a recorded route, `tools/navplan/navviz.py`.

Sibling repos with the same build/release shape: `../mod_settings` (Nexus 4885), `../in_world_navigation` (Nexus 4583), `../input_loader` (Nexus 4575). SDK/cyberpunk_cmake updates are done here first and the commits reused there.

## Where things are

- `src/red4ext/` - the plugin. `Main.cpp` = entry, dependency version checks, registers scripts/tweaks/archive/inputs with the other plugins. `Hooks/` = one game-function hook per file. `Utils/FlightModule.hpp` = hook registry macros. `Navigation/` = the Autopilot's nav map, planner (`Planner`, `RacingLine`, `Doorways`), car limits (`Vehicle`), landing pads, gates, blockers and their script bindings (`FlightNavMap`, `FlightVehicleModel`), and the Autopilot itself (`Autopilot*`, game-free; `FlightWorld` its in-game world). `Flight/FlightModeAutopilot` = the Autopilot's flight mode.
- `src/redscript/` - packed by CMake into `packed.reds` + `module.reds`. `Flight/FlightModeAutopilot.reds` is the Autopilot's script side (its fields and game glue; the mode is C++, `src/red4ext/Flight/FlightModeAutopilot`, around `Navigation::Autopilot`). `Summon/FlightSummonSystem.reds` flies a summoned vehicle to a landing pad (docs/design/vehicle-summon.md).
- `src/navigation/` - data the plugin ships (helipads, gates, blockers), generated by the tools.
- `src/tweaks/`, `src/wolvenkit/` (archive source, packed at build time), `src/audio/` (the wavs the plugin plays; every other sound is synthesised in `src/red4ext/Audio/`), `src/input_loader/` (keybinds).
- `deps/` - submodules (table below). `deps/fmod`, `deps/PhysX_3.4`, `deps/PxShared` are gitignored local SDK drops: do not delete. `deps/cyberpunk_cmake/` is our CMake framework and ships `tools/` (zoltan-clang, redscript-cli, ninja).
- `tests/` - offline unit tests (`ltbf_tests`, run by CMake and CI).
- `tools/` - offline tools, one folder per job; `tools/README.md` lists them. Machine paths come from `tools/common/paths.py` (environment variables, or an untracked `tools/common/paths.local.json` from `paths.example.json`).
- `docs/` - design notes, release and patch guides; `docs/README.md` is the index.
- The hangars are edited by hand in Blender and read back into the build (`docs/design/hangar.md`, "Editing a hangar in Blender").
- `experiments/`, `examples/` - scratch, not built. `game_dir/`, `game_dir_debug/` - build output, zipped for release.

## Build

```
cmake -B build -DCMAKE_BUILD_TYPE=RelWithDebInfo -G Ninja -DCYBERPUNK_2077_GAME_DIR=<game folder>
cmake --build build                                        # plugin, scripts, tweaks, archive, ltbf_tests
cmake --build build --target let_there_be_flight_release   # zips game_dir -> let_there_be_flight_<ver>.zip
```

MSVC 2022 (from a Developer prompt), Ninja, CMake 3.24+.

- Only `*.cpp` / `*.hpp` under `src/red4ext` are compiled (vendored C goes in as `.cpp`, see `src/red4ext/ThirdParty/miniz`). Sources are globbed at configure time: configure again after adding, moving or deleting a `.cpp` or `.reds`.
- Game version for the `.rc`/badge comes from `Cyberpunk2077.exe` FileVersion via `deps/red4ext.sdk/cmake/GetGameVersion.cmake`; in CI there is no exe so it falls back to the SDK's `RED4EXT_RUNTIME_LATEST` macro. Keep the fork's `Api/v0/Runtime.hpp` `RUNTIME_LATEST` pointing at the current patch or the release name/badge will be wrong.
- Untagged local builds get `+<branch>.<n>.<sha>` version metadata (CI builds drop it).
- `game_dir_requirements/` here also holds in-tree `input_loader.dll` / `mod_settings.dll` that report wrong plugin versions (input_loader 0.1.1, mod_settings the parent's LTBF version), so `Main.cpp`'s dependency check rejects them. Install the real Input Loader / Mod Settings release zips.
- `configure_release` regenerates `requirements.md` from `MOD_REQUIREMENTS` (own entries in root `CMakeLists.txt`, plus whatever ArchiveXL/TweakXL/RED4ext Find modules append). It is committed and appended to release notes.
- Redscript is compiled/linted against `deps/mod_settings/redscript` too (`.redscript-ide`).
- The plugin target is built by `configure_red4ext` globbing `src/red4ext` (there is no CMakeLists.txt there). The `src/redscript/codeware` submodule in `.gitmodules` is not checked out and not needed; nothing in the plugin includes Codeware headers.
- `ZOLTAN_CLANG_EXE` (found in `deps/cyberpunk_cmake/tools`, a cache variable) is only for regenerating addresses with zoltan; `configure_red4ext_addresses` is commented out, so zoltan does not run in the normal build.
- `LTBF_PHYSX34` (cache variable, default from the `LTBF_PHYSX34` environment variable) points the `flightsim` tool at a PhysX 3.4 checkout; without it flightsim builds without PhysX.

## Rebuilding the archive (WolvenKit CLI)

```
python tools/packaging/pack_archive.py           # import changed localization, pack, verify, write packed/.../let_there_be_flight.archive
python tools/packaging/pack_archive.py --check   # exit 1 if a localization json has not been packed yet
```

- The packed archive is not tracked (`src/wolvenkit/packed/` is gitignored). `cmake --build` packs it whenever a file under `source/archive/` or a localization json changes, given `LTBF_WOLVENKIT_CLI` (default: `WOLVENKIT_CLI`) or `LTBF_OODLE_DLL` (the game's `oo2ext_7_win64.dll`, copied next to the CLI, which is then downloaded). About 70 s for the 643 files. With neither, an archive already in `packed/` is shipped; with none, the build has no archive (a warning).
- CI: packing needs the Oodle dll, which cannot be redistributed. It lives in a private repo checked out by `.github/workflows/build.yaml` and `release.yaml` with the `CI_ASSETS_TOKEN` secret (read-only fine-grained token). Pull requests from forks get no secrets and build without the archive; the release workflow fails if no archive was packed. Never upload the dll as an artifact or print it.
- Every file in `source/archive/` must be tracked: the folder is gitignored, so new files need `git add -f` and do not show in `git status`. `git status --ignored src/wolvenkit/source` lists untracked ones. Changes to tracked files there stage with `git add -u <path>` (plain `git add` refuses).
- CLI: WolvenKit.Console 9.0.1 (GitHub release zip), installed at `%LOCALAPPDATA%\Programs\WolvenKit.Console\9.0.1\WolvenKit.CLI.exe`; the script downloads it if missing, `WOLVENKIT_CLI` overrides the path, with the game's `oo2ext_7_win64.dll` copied next to it. Do not use the NuGet `wolvenkit.cli` dotnet tool (`cp77tools`, stuck at 1.6.1; 8.x+ packages are not valid tools) or `%LOCALAPPDATA%\Programs\WolvenKit` (GUI, no working CLI).
- Source of truth: the CR2W files in `src/wolvenkit/source/archive/` (643 files, 548 of them the proxy collider tiles). `pack` names its output after the input folder (`archive.archive`); the script renames it.
- Localization is the only thing edited as text: change `src/wolvenkit/source/raw/user/jackhumbert/localization/let_there_be_flight.<lang>.json.json`, then run the script. It deserializes with `cr2w -d` (the `import` command silently exits 3 on these jsons) and decides staleness after a full serialize round trip, because serializing adds default fields (`primaryKey`, `maleVariant`) the raw json omits.
- Every other raw json is a stale export and must not be imported (`flight_hud.inkwidget.json` is from 2022 and predates the packed widget). Meshes, widgets, effects: edit in the Wolvenkit GUI, save into `source/archive/`, then run the script to pack.
- Other handy commands: `WolvenKit.CLI unbundle <archive> -o <dir>`, `archive <archive> --list`, `cr2w -s <file> -o <dir>` (CR2W to json). `-v` takes `Minimal`/`Diagnostic` etc., not short forms.

Game patches and reverse engineering: `docs/game-patch.md`. Releases and Nexus: `docs/release.md`.

## Conventions

- Conventional commits (`feat:` and `fix:` reach the changelog, written for players). No em-dashes. No machine paths in tracked files.
- A Mod Setting field is written back from its stored value when the mode is engaged, so a value set on that field before engaging is lost.
- Working tree normally has a dirty `deps/input_loader` (its `requirements.md` is regenerated by configure); ignore it.
- One home per fact: car limits in `Navigation/Vehicle.hpp`, the Race's route character in
  `RacePreset()` (`Planner.cpp`), the nav map format in `tools/common/navmap.py` and `NavMap.hpp`.
  Tools read them (navplan, `NAVPLAN_VEHICLE`), never copy them.
- New tools go into the `tools/` folder of their job and get a line in `tools/README.md`.
- Benchmark routes live in `tools/navplan/routes.json`; compare planner changes with
  `tools/navplan/bench.py`. The navplan target lists its sources by hand.
- CI (`build.yaml`) fails on references to private tooling or machine paths in tracked files
  (`tools/maintenance/check_public.py`).
